# OpenLife  开放人生  
## 模块化人生模拟平台完整需求任务书 v0.1

文档状态：Architecture Freeze Candidate  
版本：v0.1  
目标读者：产品设计、系统架构、游戏开发、AI 辅助开发、Module 创作者  
项目性质：长期演进型人生模拟引擎与内容平台

---

# 1. 项目定义

## 1.1 一句话定位

OpenLife 是一个具有持续世界历史、人物认知、家族传承、可学习决策行为、模块化规则和多时间线能力的人生模拟平台。

玩家不是在完成一套固定人生流程，而是在一个会持续存在、可以被理解、改变、继承和留下痕迹的世界中生活。

---

# 2. 核心愿景

OpenLife 不以“刷最高属性”“找到唯一最优路线”“完成固定剧情”作为主要目标。

项目最终希望提供四种核心体验：

1. 活一个人的人生
2. 见证一个家族延续
3. 影响一个长期存在的世界
4. 让自己的选择成为历史的一部分

玩家第一代死亡后：

- 家族继续存在；
- 公司可能继续经营；
- 学校可能成为百年机构；
- 著作、发明、建筑、组织可能留下；
- NPC 会继续生活；
- 后代可以面对祖先留下的问题和机会；
- 其他玩家甚至可能在未来进入这个历史。

核心体验不是：

 “这一局我拿了多少分。”

而是：

 “我这一生留下了什么？”

# 4. 架构最高原则

OpenLife 必须遵守以下不变量。

## INV-001 世界状态只能通过事务修改

任何系统不得直接：

```text
player.money += 1000
```

必须：

```text
Command
↓
Validation
↓
Rule Resolution
↓
Effects
↓
Transaction
↓
State Mutation
↓
Events
```

---

## INV-002 外部输入全部转换为 Command

包括：

- 玩家输入；
- UI；
- AI；
- AutoSim；
- 网络；
- 世界服；
- Module；
- 外部现实数据。

全部不能直接修改 State。

---

## INV-003 AI 不拥有世界状态

AI 可以：

- 解析意图；
- 生成叙事；
- 推荐行动；
- 控制授权范围内的角色；
- 生成内容草案。

AI 不允许：

- 自行修改存档；
- 自行修改属性；
- 自行决定已经发生的事实。

---

## INV-004 相同输入必须可复现

在以下条件一致时：

```text
State
Command
World Seed
Rules
Module Versions
```

必须得到相同结果。

系统随机数必须来自统一 Deterministic RNG。

---

## INV-005 世界真相和人物认知分离

必须始终满足：

```text
Fact
≠
Observation
≠
Knowledge
≠
Memory
≠
Belief
```

角色不知道的事情，不得因为系统知道而自动获知。

---

## INV-006 历史实体可以消失，历史记录不能消失

公司可以倒闭。

人物可以死亡。

建筑可以拆除。

但重要 Historical Record 不得因为实体失效而删除。

---

## INV-007 Module 不能成为第二套引擎

Module 不允许：

- 绕过 Transaction；
- Monkey Patch Core；
- 直接修改其他 Module 私有数据；
- 自己维护另一套世界真相；
- 自己维护另一套全局随机数；
- 绕过 Capability 权限。

---

## INV-008 玩家人生时间不得直接控制公共世界时间

玩家的：

```text
Life Clock
```

与：

```text
World Clock
```

必须逻辑分离。

个人快进不得强制其他玩家推进时间。

---

# 6. 核心对象层级

必须明确区分四个概念：

```text
Human User
↓
Player Profile
↓
Life  Lineage
↓
Character
```

## Player Profile

属于用户，而不是某个角色。

保存：

- Player Style；
- AutoSim 偏好；
- AI 使用偏好；
- UI 设置；
- 隐私设置。

---

## Lineage

代表一条玩家家族连续线。

保存：

- 家族身份；
- 祖先；
- 后代；
- 家族遗产；
- 家族重大历史；
- 长期家族资产；
- 家族声誉；
- 家族秘密。

---

## Character

代表具体人物。

拥有：

- Entity；
- Components；
- Relationships；
- Memory；
- Knowledge；
- Belief；
- Personality；
- Goals；
- Life History。

死亡后转为 Historical Entity。

---

# 7. World Model

禁止使用不断膨胀的超级 Player 类。

采用：

```text
Entity
+
Component
+
Relation
```

思想。

例如：

```text
character1001

components
  core.identity
  core.health
  modern.wealth
  career.current
  magic.mana
```

Module 可以注册自己的 Component。

---

# 8. Relation Graph

关系不得分散存储。

例如：

```text
A -- parent_of -- B
A -- married_to -- C
A -- employed_by -- Company
A -- owns -- Property
A -- member_of -- University
```

Relation 可以拥有 Component。

例如：

```text
friendship
closeness
trust
history
```

---

# 9. Organization  Institution

组织必须是一等 Entity。

用于表达：

- 公司；
- 学校；
- 医院；
- 政府；
- 政党；
- 社团；
- 教会；
- 黑帮；
- 研究机构；
- 魔法学院。

组织可以比人物活得更久。

这是长期历史系统的重要基础。

---

# 10. Family

Family 建议作为一等 Entity。

它可以拥有：

```text
Members
Assets
Reputation
Debt
Property
Businesses
Culture
Traditions
Secrets
Historical Records
```

代际系统不得简化为：

```text
上一代财富 × 20% → 下一代
```

核心应该是：

 世界状态继承。

---

# 11. 世界状态与派生状态

所有状态必须区分：

## Primitive State

权威原始数据。

例如：

```text
birth_date
relationship
property_owner
```

---

## Derived State

通过 Query 计算。

例如：

```text
age
is_married
current_employer
family_net_worth
```

Derived State 原则上不得重复持久化。

---

# 12. Simulation Kernel

Kernel 必须尽量小。

v0.1 Stable Kernel 仅负责：

```text
Command
Validation Boundary
Transaction
Clock
Deterministic RNG
State Mutation
```

Kernel 不知道：

- 历史；
- 魔法；
- 婚姻；
- AI；
- 科技；
- 公司。

---

# 13. Command  Effect  Event

严格区分。

## Command

“想做什么。”

例如：

```text
ApplyForJob
StartBusiness
MoveCity
ConfessLove
```

---

## Effect

世界状态需要发生的具体修改。

标准 Effect 建议包含：

```text
SetComponent
ModifyValue
AddRelation
RemoveRelation
SpawnEntity
ArchiveEntity
AddFact
AddMemory
ScheduleTask
```

---

## Event

已经发生了什么。

例如：

```text
CompanyFounded
RelationshipStarted
CharacterMoved
JobAccepted
```

---

# 14. Rule Engine

规则分三类。

## Constraint Rule

判断能否执行。

---

## Resolution Rule

判断执行后结果如何。

---

## Reaction Rule

某件事发生后其他系统如何响应。

执行链：

```text
Command
↓
Constraint
↓
Resolution
↓
Effects
↓
Transaction
↓
Event
↓
Reaction
```

---

# 15. Modifier System

所有复杂数值计算应尽量通过统一 Modifier Pipeline。

例如：

```text
Job Success

Base
+ Education
+ Experience
+ Reputation
+ Referral
- Economic Recession
- Criminal Record
```

Modifier 必须记录：

```text
source
scope
reason
priority
duration
```

系统必须能够生成 Decision Trace。

---

# 16. Explainability

复杂模拟必须可解释。

例如：

```text
Divorce triggered

Primary causes
- trust very low
- financial stress
- affair discovered
```

Debug 层必须能够回答：

 为什么发生？

这是防止玩家把复杂模拟理解成“随机整人”的关键。

---

# 17. Scheduler

禁止所有 Module 全量执行：

```text
onTick()
```

统一使用 Scheduler。

例如：

```text
Salary → monthly
Birthday → yearly
Economic update → quarterly
Weather → daily
```

AutoSim 快进时直接跳到下一重要事件。

---

# 18. Simulation LOD

世界不能完整精细模拟所有 NPC。

建议：

```text
L0
玩家本人  核心人物
完整模拟

L1
家人  好友  同事
高精度

L2
普通社会 NPC
低精度

L3
背景人口
统计模拟
```

---

# 19. Entity Materialization

普通背景人口不必全部拥有完整 Entity。

例如：

```text
城市中有8000名医生
```

可以首先存在于 Population Model。

玩家与某医生真正发生关系时：

```text
Materialize NPC
```

一旦形成长期关系或重要历史，该 NPC 永久化。

---

# 20. Mind Runtime

人物必须拥有自己的认知世界。

核心结构：

```text
Fact
↓
Observation
↓
Knowledge
↓
Memory
↓
Belief
```

并可增加：

```text
Mental Model of Others
```

人物可以错误理解别人。

---

# 21. Perception  Fog

OpenLife 应支持三种认知遮罩。

## Spatial Fog

不知道远处发生什么。

## Social Fog

不知道：

- 秘密；
- 他人真实意图；
- 私人关系。

## Epistemic Fog

不知道：

 世界本身如何运行。

这是知识、科技、魔法发现的重要基础。

---

# 22. Fact  Knowledge  Memory  Belief

必须严格区分。

例：

```text
Fact
父亲因入狱离开家庭

Memory
小时候父亲突然消失

Belief
父亲主动抛弃了我
```

三者可以不同。

---

# 23. Knowledge  Discovery Runtime

Core 不规定：

- 原子；
- 电力；
- 魔法；
- 经脉；
- 灵魂。

但提供：

```text
Phenomenon
Observation
Theory
Evidence
Knowledge
Discovery
Capability
```

系统逻辑：

```text
Reality
↓
Observation
↓
Theory
↓
Evidence
↓
Knowledge
↓
Engineering
↓
Capability
```

---

# 24. World Law 与 Knowledge 分离

例如：

```text
Reality
物质确实由原子构成
```

不等于：

```text
Civilization Knowledge
已知道原子结构
```

文明必须通过发现逐渐理解世界。

---

# 25. World Pack

World Pack 定义：

```text
Law Model
Ontology
Phenomena
Environment
Initial Knowledge
Discovery Rules
Civilization Defaults
```

例如现实世界：

```text
matter
energy
biology
electromagnetism
```

魔法世界：

```text
matter
mana
soul
magic law
```

---

# 26. Ontological Truth

世界创建时必须固定基础规律。

例如：

```text
是否存在灵魂
是否存在魔力
死亡是否可逆
时间是否线性
```

这些不能在运行几十年以后临时决定。

---

# 27. Latent Truth

世界可以存在尚未展开、但已由 Seed 确定的真相。

例如：

```text
地下是否存在矿藏
遥远星球有什么
```

角色不知道，不代表世界没有。

---

# 28. Technology

Technology 不进入 Core。

它是以下抽象的组合：

```text
Knowledge
+
Capability
+
Process
+
Dependency
```

避免固定科技树。

建议采用 Knowledge Graph。

---

# 29. 通用 Resource  Flow  Network

Core 只知道：

```text
Resource
Flow
Network
Process
```

现实世界：

```text
electricity
power_grid
```

魔法世界：

```text
mana
ley_line
```

修仙：

```text
qi
meridian
```

都使用同一套底层。

---

# 30. Capability Dependency

Module 不应强依赖具体实现。

例如住宅模块：

```text
requires
energy.distribution
```

现实世界由：

```text
electric.grid
```

提供。

魔法世界由：

```text
mana.grid
```

提供。

---

# 31. History Runtime

历史是 OpenLife 的核心系统之一。

必须区分：

```text
Event
Fact
Historical Record
Lineage Chronicle
```

不是所有事件都进入公共历史。

---

# 32. Historical Significance

事件可具有：

```text
historical_significance
```

例如：

```text
早餐        0.001
结婚        0.2
建立医院     0.6
创建全国企业  0.85
改变世界科技  0.99
```

用于决定：

- 是否进入历史；
- 是否被社会记录；
- 是否进入后代认知；
- 是否进入公共 Timeline。

---

# 33. Legacy Entity

人物死亡不意味着创造物消失。

Legacy Entity 包括：

```text
Property
Company
School
Book
Artwork
Patent
Foundation
Institution
Monument
```

后代可以继续接触。

---

# 34. Causal Graph

重要 Event 必须支持：

```text
caused_by
```

形成：

```text
Economic Crisis
↓
Company Loss
↓
Layoff
↓
Unemployment
↓
Family Stress
↓
Divorce
```

未来可以用于：

- Debug；
- AI 传记；
- 历史解释；
- 人生回顾。

---

# 35. 世界  Timeline  LifeSave

必须严格区分。

## World


## Timeline



---

# 36. 多时间线

世界服允许存在多个 Timeline。

采用：

```text
Shared Main Timeline
+
Branches
```

但不得：

 每个普通选择都创建分支。

只有发生无法兼容的因果冲突时才 Fork。

---

# 37. 历史补录优先于 Fork

过去玩家上传行为时：

```text
Historical Upload
↓
Conflict Analysis
```

优先：

```text
Add
Extend
Catch-up
```

无法保持因果一致时：

```text
Fork
```

原则：

 能补录，不分叉。

---

# 38. Timeline 分支类型

建议：

```text
Personal Branch
Shared Branch
Public Branch
```

无人使用时：

```text
ACTIVE
↓
DORMANT
↓
ARCHIVED
```

仅保存 Snapshot + Delta。

---

# 39. Family Lineage Continuity

无论公共历史如何变化，玩家家族重大历史不得丢失。

例如：

```text
第一代创建A公司
```

即使：

```text
A公司50年后倒闭
```

后代仍可看到：

 该公司由祖先创建。

---

# 40. Autonomy Runtime

必须支持统一：

```text
DecisionProvider
```

实现：

```text
HumanDecisionProvider
RuleDecisionProvider
PlayerStyleDecisionProvider
CharacterDecisionProvider
AIDecisionProvider
RandomDecisionProvider
```

最终都只输出 Command。

---

# 41. AutoSim

AutoSim 不是简单加速时间。

支持：

```text
模拟到下一年
模拟到毕业
模拟到找到工作
模拟到30岁
模拟到重大事件
模拟到角色死亡
```

---

# 42. Autonomy Policy

AutoSim 必须允许玩家配置授权。

例如：

```text
日常消费      自动
普通社交      自动
换工作        询问
结婚          永远询问
生育          永远询问
创业          询问
犯罪          永远询问
```

---

# 43. Player Style Model

这是平台级 Simulation Service。

不是 Kernel，也不是普通 Mod。

底层提供：

```text
BehaviorEvidence
PreferenceModel
DecisionPolicy
```

具体倾向维度允许 Module 扩展。

---

# 44. Player  Roleplay  Character 三种倾向

必须分离：

```text
Player Style
玩家长期玩法习惯

Roleplay Style
当前这一局希望怎么玩

Character Personality
角色世界内真实性格
```

AutoSim 可选择参考哪一种。

---

# 45. Behavior Evidence

只能从已经 Commit 的行为形成。

不能因为：

 玩家浏览过按钮

就判断倾向。

流程：

```text
Player Choice
↓
Command
↓
Transaction Commit
↓
Decision Event
↓
Behavior Evidence
↓
Preference Model
```

---

# 46. Player Style 隐私

Player Style 默认：

- 本地保存；
- 可关闭；
- 可重置；
- 可查看摘要；
- 不应自动上传世界服务器。

它描述的是：

 游戏决策习惯。

不得宣称为现实人格诊断。

---

# 47. NPC Mental Model

NPC 可以根据自己观察到的行为形成：

```text
Belief About Character
```

例如：

```text
trustworthy
risk-taking
family-oriented
```

这不是角色真实属性，而是 NPC 的理解。

允许：

 误判。

---

# 48. AI Runtime

AI 是 Adapter，不是 Core。

建议能力接口：

```text
IntentProvider
NarrativeProvider
DialogueProvider
PlanningProvider
ContentGenerationProvider
MemorySummaryProvider
```

---

# 49. AI 长期记忆

AI 本身应视为无状态计算器。

真正长期记忆保存在 OpenLife：

```text
World Facts

Belief
Knowledge
Summary
Semantic Index
```

AI 每次只获得 Context Projection。

---

# 50. AI NPC

# 96. 时间与纪元模型（方向修订 · 2026-10-07 记录）

> 本节由项目所有者口述，作为方向性修订记录。
> 状态：**Adopted（起点已实施 2026-10-07）** —— 起点锚点与纪元渲染已落地，
> 上古→现代的 World Pack 内容填充仍待办。

## 96.1 修订动机

当前实现把世界起点硬编码在现代（`apps/web/server.ts` 用 `2000 + tick/12` 换算年份），
等于让世界在 2000 年凭空开始。这与"持续存在的世界历史"这一核心愿景冲突。

## 96.2 起点锚点

**起点 = 公元前 2070 年（夏朝建立）**。

```text
tick 0  =  公元前 2070 年
```

选择理由：有史可考、上限清晰（到当代约 4096 年），且以后填充夏商周内容时
年份可直接对齐真实史料，无需反向换算。

契约层：

```ts
export const ERA_START_YEAR = -2069;   // 天文纪年；formatYear(-2069) = "公元前 2070 年"
export function formatYear(year: number): string   // "公元前 2070 年" / "公元 2026 年"
export function yearOfTick(tick: number, eraStartYear = ERA_START_YEAR): number
export function tickOfYear(year: number, eraStartYear = ERA_START_YEAR): number
export function formatTick(tick: number, eraStartYear = ERA_START_YEAR): string
```

注：内部用天文纪年（负数 = 公元前，且存在 0 年 = 公元前 1 年），
对外渲染统一走 `formatYear`，不暴露天文纪年的负数细节。

## 96.3 修订后的时间观

世界时间锚定在**真实历史时间轴**上：

```text
上古 → 夏 → 商 → 周 → 春秋战国 → 秦 → 汉 → ... → 唐宋元明清 → 近现代 → 当代
```

要求：

1. 纪元使用真实纪年，包含 **公元前（BC / BCE）** 与 **公元后（AD / CE）** 两段；
2. 时间原点不是 2000 年，而是夏朝建立的公元前 2070 年；
3. 世界从最早的时代开始，**由玩家与内容生产逐步向后填充**到现代，
   而不是从现代倒推或直接开局于现代；
4. 填充过程本身即世界历史的一部分——早期时代留下的记录必须能被后世看见。

## 96.4 已实施（2026-10-07）

- [x] `life-contracts` 引入 `ERA_START_YEAR` 纪元锚点；
- [x] `formatTick` 的 `startYear` 从"声明未用"改为真实生效的 `eraStartYear` 参数；
- [x] 支持公元前年份的格式化（`formatYear`）与界面渲染；
- [x] 移除 `apps/web/server.ts` 中的 `2000` 硬编码，改为从契约取；
- [x] 新增 `tests/unit/era-calendar.test.ts` 锁定纪元语义（83/83 通过）。

## 96.5 待办

- [ ] 定义 `Era`（纪元）Core Primitive 是否成立，走 §80 Core 升格规则评估；
- [ ] 规划从上古到现代的 World Pack 内容填充顺序；
- [ ] 评估早期时代的内容密度：一年一年模拟夏朝，玩家可能要按数万次"让一年流逝"，
      是否需要"时间跳跃"作为一等概念（注意：内核惰性，不 advance 不产生 tick，
      故性能不是问题，体验才是）。
