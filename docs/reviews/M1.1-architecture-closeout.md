## 1. 时间系统 — ISSUE（高）

### 现象

`world-clock` 用**日刻度**读同一个 tick（360 tick = 1 年），而 `life-contracts` 与 `apps/web` 仍用**月刻度**读它（12 tick = 1 年）。两者读的是同一个数字，却给出两个答案，且同时出现在一份 API 响应里。

实测（`ISSUE: yearOfTick and ageInYears read day ticks with month-scale arithmetic`）：

```text
DAYS_PER_MONTH = 30   DAY_TICKS_PER_YEAR = 360   TICKS_PER_YEAR = 12

tick=360（恰好一个日尺度年）
  monthsElapsed(360) = 12        ← world-clock，正确
  yearOfTick(360)    = -2039     ← life-contracts，应为 -2068（差 30 倍）
  ageInYears(0, 360) = 30        ← 360 天大的角色被报成 30 岁
```

玩家可见（`ISSUE: the running server reports an era a player can see diverging from its own clock`）：

```text
推进 360 天后
  clock.yearsElapsed        = 1     ← 正确
  yearOfTick(tick) 推出的年 = 30    ← 同一份 payload 里，时代已多走 29 年
```

漂移随年数线性增长（`ISSUE: the era drifts about 29 years for every year actually played`）：

| 实际经过 | 时代显示多走 |
| --- | --- |
| 1 年 | 29 年 |
| 5 年 | 145 年 |
| 100 年 | 2900 年 |

### 根因

`packages/life-contracts/src/modern.ts` 的 `yearOfTick` / `tickOfYear` / `ageInYears` / `formatTick` 全部除以 `TICKS_PER_YEAR`（12）。这些函数在 M1 之前是正确的；M1 引入日刻度后，它们被继续用于日尺度 tick，于是单位失配。

`apps/web/server.ts` 是主要受害者：第 240–242 行用 `yearOfTick` 生成 `year` / `era`，第 241 行用 `tick % 12 + 1` 生成 `month`，而同一份 `gameState()` 里 `clock` 字段来自 `world-clock`。

### 影响面（全量扫描结论）

仍然按旧月刻度读取原始 tick 的模块：

| 模块 | 位置 | 当前是否已失真 |
| --- | --- | --- |
| `apps/web/server.ts` | `year` / `month` / `era`、ageOf、autosim 的年份步长 | **是，玩家可见** |
| `modules/world-time` | `seasonPhase = (c.at % 12) / 12` | 是（季节相位被压缩 30 倍） |
| `modules/basic-autonomy` | `afterTicks/everyTicks: TICKS_PER_YEAR` | 是（年度决策改为每月触发） |
| `modules/early-civilization` | 同上，`preservationIntervalTicks: 40 * TICKS_PER_YEAR` | 是 |
| `modules/family` | `bornAt = tick - TICKS_PER_YEAR * rng.nextInt(20,35)` | 是（NPC 年龄被算成月） |
| `modules/modern-world` | `modern.annual_tick`（每 12 tick） | 是（每年触发 30 次） |
| `modules/education` / `career` | `TICKS_PER_YEAR` 派生时长 | 是 |

**这些不是 M1 引入的 bug，而是 M1 之前"12 tick = 1 年"的约定在日刻度下不再成立。** M1 只改了玩家可见的那一层，未同步其余消费者。

### 建议修复方向（未实施，留待裁决）

不改 Kernel。在 `world-clock` 已提供正确换算的前提下，最小收口是把**月/年派生统一走一个门面**：

1. `life-contracts` 的四个时间函数改为接受「尺度」参数，或新增 `dayYearOfTick` 系列；旧名保留但标注为月刻度专用。
2. `apps/web/server.ts` 的 `year`/`month`/`era` 改读 `clockReading()`，删掉 `tick % 12 + 1`。
3. `world-time` 的 `seasonPhase` 改用 `monthOfYear(tick)`。
4. 年度调度（`modern.annual_tick`、`basic-autonomy`、`early-civilization`）的 `afterTicks` 从 `TICKS_PER_YEAR` 改为 `DAY_TICKS_PER_YEAR`，或改由 `world-clock` 的月度脉冲驱动。

第 4 项会改变既有行为，建议先补一个「一年恰好触发一次」的测试再改。

## 2. 空间系统 — ISSUE（中）

### 职责边界（现状，清晰）

| 层 | 模块 | 负责 | 归属关系 |
| --- | --- | --- | --- |
| 世界空间 | `world-geography` | Region / Location / 连通 / 边界锚点 | `contains`、`adjacent_to`、`located_at` |
| 聚落空间 | `world-space` | 场所 Place / 空间 Space / 出入口 / 容量 | `inside`、`occupies`、`standing_in` |
| 聚落内容 | `settlement-locations` | 具体场所、居民、资源点、实例 | 复用上两层的命令 |

这个分层本身是合理的，不构成重复架构。

### 问题一：两套位置事实，互不感知

`ISSUE: a person can hold two independent position facts with nothing reconciling them`

```text
macro 层： world-geography.place_entity → located_at → L1
micro 层： world-space.occupies → （无）
```

同一人物同时存在两条互不相干的位置事实，且**没有任何代码交叉校验**。目前之所以没爆，是因为 `settlement-locations` 从不写 `located_at`；但 `world-geography.place_entity` 是公开命令，任何模块（或 AI Adapter）都能写出第二个位置。

### 问题二：聚落未锚定到宏观 Geography

`ISSUE: settlement places are not bound to a macro geography Location`

```text
place:yard.locationId   = ""   （空，未绑定）
settlement.locationId   = ""   （空，未绑定）
```

`locationId` 只是一个**字符串字段 + 约束检查**，不是关系。装载 `packs/xia_starter_v0_1`（40 个 Location）后，聚落仍然"何处都不在"。M1 允许无地图运行（地理为软依赖）是有意的，但**当前即使有地图，聚落也不会自动锚定**。

### 建议修复方向（未实施）

- 定 `world-space.place` 为**唯一微观位置权威**，`world-geography.located_at` 明确降级为「宏观区域归属」，并在文档与约束中写死二者不得互相覆盖。
- 聚落落地时，把 `locationId` 从字符串改为 `world-space.anchored_at` 关系；有地图时强制非空。
- 增加一条不变量检查：任何人物至多一条 `occupies`（已由存储层唯一索引保证）且至多一条宏观归属。

## 3. 关系存储 — PASS（唯一性）/ ISSUE（历史与审计）

针对 `archiveRelation` / `addRelation` 的修改，按要求执行了 `创建 → 归档 → 重建 → 重复 → 存档读取` 回归。

### 通过的部分

`PASS: cut and re-join keeps exactly one live relation and never accumulates`

```text
连续 3 轮 cut/join：
  每次 cut 后 live = 0（正反两个方向都清除）
  每次 join 后 live = 1（每方向恰好一行）
  总行数恒定为 2，从不累积
```

`PASS: a cut/join cycle still survives save and load exactly` — 3 轮循环后 save/load 指纹一致。

结论：**索引正确性没问题，活跃关系唯一性没问题，不会出现关系泄漏或重复。**

### 问题一：重建会销毁归档行

`ISSUE: re-joining the same pair destroys the archived relation row`

```text
cut   → 归档行 rel:r2（archivedAt 已设）
join  → rel:r2 被删除，新建 rel:r5
cut   → 归档 rel:r5
join  → rel:r5 被删除，新建 rel:r9
```

每轮重建都会删除前一个归档行。**同一对实体的关系行历史不累积**，且关系 ID 每轮变化。

注意：这是我本次修复的直接后果。修复前 `addRelation` 遇到归档键会直接抛错（`relation already exists`）；修复后改为复用槽位，于是"复用"表现为"删除归档行"。功能上更可用，但代价是历史行被丢弃。

### 问题二：关系变更不产生事件

`ISSUE: relation churn leaves no event trail, so the replacement is not auditable`

```text
connect_locations  → eventIds.length = 0
disconnect_locations → eventIds.length = 0
```

`world-geography` 的关系效果一律带 `announce: false`。叠加问题一，一次 cut/join 在**关系行与事件日志里都不留痕迹**。

严重度评估：比看起来低，但要写清楚——`addRelation` / `removeRelation` 的 `announce` 默认是 `true`，只有 `world-geography` 主动传了 `false`。因此受影响的是地理连边，而非家庭或产权关系（`family.parent_of` 走事件路径，历史仍在）。真正后果是：**宏观连通性的变更无法回答"这条路以前通过吗"**，这对 M5 的历史回放与 SCENE-C（离开数日再回来）是可感知的。

### 建议修复方向（未实施）

- 若要保留关系行历史：`addRelation` 复用槽位时**不要删除**归档行，改为给新行分配新 ID 并让索引指向新行（索引是 `Map<key, id>`，本就只存一个当前 ID，无需删行）。
- 地理连边补一个低重要性事件（`historicalSignificance: 0.02`），或至少让 `place_entity` 保留审计。
- 补一条回归：同一对实体连续 10 轮 cut/join 后，归档行数应线性增长而非恒为 1。

## 6. 借物与偷窃 — ISSUE（中）

你的裁决是「借用与偷窃不能混成一个动作，且借用不应永远默认 NPC 同意」。核查结果：

**借用侧符合要求。** `PASS: lending is a distinct owner-issued act that grants custody without ownership`：

```text
lend 由所有者发起（actorId = owner）
  所有权不动，保管权转移，记录 dueAt
  重复出借被拒：E_OBJECT_IN_USE
```

**但规则层没有区分借用与拿取。** `ISSUE: taking another household's property is allowed by the rule layer, and records no loan`：

```text
直接派发 world-objects.take（actorId = 玩家）on 邻居家的陶罐
  ok = true
  保管权 → 玩家
  所有权 → 仍属邻居（这点是好的）
  loan 记录 = undefined   ← 无债务
```

也就是说：**"借用 vs 偷窃"的区分目前只存在于 `apps/web/src/player.ts`**，它把玩家的 `take` 重写成由房主发起的 `lend`。任何绕开 Web 的驱动（AI Adapter、AutoSim、debug console、其他模块）都能直接 `take`，且不留债务。

这恰好是你担心的形状：**规则在适配器里，而不在世界里。** M3 要完善"意愿、关系、信誉和拒绝理由"时，如果先修规则层，M3 就只需要填判定函数，不必重构。

### 建议修复方向（未实施）

- `world-objects.take` 增加所有权约束：非本人所有且未被许可时，要么拒绝，要么转为显式 `steal`（记录见证、风险与关系后果）。
- 把「玩家 `take` → 房主 `lend`」的包装从 `apps/web` 下沉为世界内的一个命令（如 `world-objects.request_loan`），使所有驱动走同一条规则。
- NPC 是否同意在 M1 保持确定性规则即可，但**判定位置应在规则层**，M3 只替换判定内容。
