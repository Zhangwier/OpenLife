# OpenLife：低饱和像素乡野、横屏生活地图细化方案

日期：2026-10-25。性质：独立研究与设计建议，不是实施记录。目标：供用户与正在开发的 AI 选择性采用。

本轮仅查阅项目、用户两张参考图、已有截图与公开资料；没有修改仓库、运行游戏、启动测试或服务，也没有向其他 AI 派发任务。文档存放在项目外，避免干扰开发。仓库读取时 HEAD 为 `8b3a0b5`，工作区存在进行中的修改；以下代码观察是读取时快照，交接前应由实现者核对。

## 1. 建议确定的产品方向

**以低饱和、自然比例的像素乡野作为视觉中心，制作横屏、直接操控一个人物的河岸生活游戏。玩家通过走动、观察、劳作与交往理解世界；NPC 有自己的需要与生活，重要选择会留下实物、关系和代际后果。**

三个已经确定的前提：横屏；减少常驻文字；单人生活探索＋NPC 自主生活。

本方案建议采用“人工设计场景骨架＋可复用像素素材＋确定性自然细节”的混合制作方式。先做一段可生活的河岸小村，再扩地图。保留 OpenLife 的个人生活、人物认知、物品归属与传承特色。

参考分工：星露谷式直接行动与日常目标、RimWorld 式人物需求和自主行为，服务于单个人的生活体验。玩家默认没有指挥全村、查看全部人隐私或随意拿取财物的权限。

## 2. 参考图究竟值得学什么

两张用户截图是本方案最直接的视觉依据。下述分析来自肉眼观察，不是对源素材像素、调色参数或原作者制作工具的反向测量。

| 维度 | 图中观察 | OpenLife 应采用的设计 |
|---|---|---|
| 画面组织 | 林缘不规则，道路绕过植被与建筑，人物位于较易辨认的空地 | 每个场景先划出活动区、通路、边界和视觉焦点，再铺细节 |
| 人物比例 | 四肢和躯干偏修长，头部不过大 | 建立统一角色模板，衣服、发型、姿态识别人，避免人人同款小木偶 |
| 植被 | 树冠彼此遮挡，内部有大明暗团块和局部碎叶；地被高低不同 | 先设计树形与体积，再以叶簇打破边缘；禁止全屏均匀撒噪点 |
| 色彩 | 苔绿、橄榄绿、泥褐形成底色，浅衣服与少量花叶吸引视线 | 将稀少的亮色分配给人物、入口与关键物，不整体去饱和到灰泥色 |
| 纵深 | 树干、屋顶、篱笆与前景树冠互相遮挡 | 按脚底位置排序；屋顶、树冠独立拆层；前景不能长期盖住玩家 |
| 留白 | 道路和人物周围比树林安静 | 可走区域低细节，背景植被高细节，操作区域对比清楚 |
| 生活感 | 房屋、工作区域、草路形成用途明确的空间 | 晾晒区有半成品、河边有取水点、窑旁有柴堆；画面说明用途 |

图一更适合定义村落的活动场景，图二适合定义林间过渡场景。不能拿图二的遮挡密度套到所有日常操作区域。

截图水印为 NicoDocci。其官方 Steam 页面将《A Kingdom of Soil》描述为中世纪像素角色扮演与经营冒险，开发者同为 NicoDocci，可作为参考来源线索；本轮没有确认这两帧具体出自哪段视频，也没有验证其引擎与完整素材管线。[官方页面](https://store.steampowered.com/app/3991390/A_Kingdom_of_Soil/)

OpenLife 当前世界设定是早期河岸聚落。建议保留参考图的视觉语言，另做符合本项目的夯土、木骨、茅草、编织、陶器与服饰设计。中世纪窗格、酒馆、石砌烟囱等不能因为参考图好看就成为世界观默认。这里是题材一致性建议，不声称完成考古考证。

## 3. 项目现状与优先补齐项

本轮阅读了协作指南、玩家路径验收、手机路线、第一季定义、世界设定、时间 RFC、像素接入说明、像素美术规格，以及像素渲染、显示模式与空间模块的相关代码。查看了已有 `artifacts/art/restore-art-placeyard-秋-晴.png`，未重新生成截图；它只证明文件中呈现的状态，不代表正在开发版本的最终画面。

| 当前观察 | 对目标体验的影响 | 建议优先级 |
|---|---|---|
| 已有截图房屋居中、树木分列、人物集中排列 | 更像展示场景，缺少自然空间和生活动线 | P0：先重做一张母场景的构图 |
| `pixel-scene.js` 中 NPC 按数组索引站位，玩家位置固定 | 画面位置不能证明角色真实走到这里 | P0：位置与可交互对象建立权威映射 |
| 该渲染器每帧顺序为建筑、道具、人物、整张树冠 | 不能仅凭已有顺序保证所有前后遮挡正确 | P0：按可排序对象拆层，并做屋顶遮挡处理 |
| SceneVM 截取前 6 人、12 物件、8 出口 | 若直接用于正式地图，可能裁掉重要对象或入口 | P0：由视野和重要性交互决定展示，保留完整可达目标索引 |
| 像素视图说明仍定位为只读展示；读到的 `view-mode.js` 默认文字 | 独立像素页与正式可玩横屏入口需要明确衔接 | P0：实际入口与用户路径单独验收 |
| 已有活动额度与日尺度；画面用额度比例推断光照 | 日内钟点与自主行走不能由渲染动画擅自创造 | P1：统一时间语义后再增加时段生活 |
| 有自治、物品、关系、生产、传承等既有系统 | 最大收益是把真实变化画出来 | P1：做视觉状态映射，不再建立第二份模拟 |

不建议依据旧计划或之前对话中的实现状态覆盖当前磁盘事实。本轮并未断言其他分支或另一位 AI 的工作缺失。

## 4. 现有美术规格应修订的地方

以下是对 `docs/design/pixel-art-style-spec.md` 的建议，未修改原文件。

1. **把“没有黑描边”改成“避免统一闭合的黑色轮廓”。** 现规格要求外轮廓明度差不能大于内部分层，过于绝对。人物站在暗林前、树干前后交错时需要局部强对比。验收应看形体是否自然且可辨认，不以所有边缘服从一个不等式代替审美判断。
2. **统一逻辑像素与显示像素。** A9 指定 PIX=2/3，A10 又要求 1–2px 叶片，很容易使不同函数各用一套单位。建议下面所有素材尺寸均指逻辑像素，成图统一最近邻显示；1px 叶尖和 2px 叶簇可共存于同一逻辑网格，禁止运行时任意缩放破坏像素尺度。
3. **取消全树必须固定镂空 25%–45% 的硬指标。** 用户截图经过显示缩放和视频压缩，无法从中推出原素材透明比例。将镂空集中在边缘、枝间；核心体积保留连贯色块，防止树像筛网。
4. **有序抖动作为局部工具，不作为全局纹理。** 大面积 Bayer 格纹容易出现机械棋盘感。优先画叶簇和材质，再局部抖动过渡；以静止及移动镜头中是否稳定为准。
5. **道路亮边随光向和地被变化。** 不给所有道路套完整等宽荧光线；踩踏边可有裸土、稀草、破口和局部亮草。
6. **保留少量暖色，但不给橙树固定全年义务。** 春夏焦点可以是浅衣、花、陶土，秋季再用橙叶；雪天通过色块面积和材质分层，不能只把绿色变白。
7. **确定性截图增加动画时间参数。** 相同地点、季节、天气、种子仍可能处于不同落叶/摆动帧。静态地形要求一致；整帧比较还需固定镜头、角色状态、动画时刻、分辨率及素材版本。
8. **将地形种子与天气种子分开。** 地图骨架绑定世界种子、地点和布局版本；天气只改变外观与粒子。不要让天气进入某个公共 seed 后被未来植被布局复用，导致下雨时树搬家。

## 5. 建议冻结的美术基准

以下数字是首轮建议值，用于小样校准，不是从截图精确提取的参数，也不是已经测得的性能。

### 5.1 视角、像素与比例

采用能看见屋顶与建筑正面的斜俯视二维表现；地面以正交坐标组织，不引入等距菱形网格复杂度。物理地图格线默认不显示。

| 项目 | 首轮建议 | 约束 |
|---|---|---|
| 参考画布 | 640×360 逻辑像素 | 用于风格母版；不是所有手机强制同一显示尺寸 |
| 地图基础单元 | 16×16 逻辑像素 | 碰撞格可更细，但不要与贴图大小混为一谈 |
| 成人可见高度 | 28–32px | 建议统一 32×48 帧画布，脚底锚点相同 |
| 主路有效宽度 | 40–56px | 允许 NPC 会车和玩家绕过，不被装饰草侵占 |
| 支路有效宽度 | 24–32px | 少量狭窄林径可以更窄，入口必须辨认清楚 |
| 门洞视觉高度 | 30–38px | 与人比例一致；门前留交互站位 |
| 房屋整体轮廓 | 宽 100–160px、高 80–130px | 大建筑允许更大，但应拆屋顶和墙体 |
| 乔木整体高度 | 80–140px | 冠幅按树种变化；禁止统一圆球和统一等距排列 |
| 灌木 | 16–40px 高 | 与草、人物、树形成四级高度 |

UI 用清楚的正常中文字体与 CSS 尺寸绘制，不跟随世界画面降采样。小字不强行做点阵字体。

像素显示先关闭图片缩放平滑，坐标在渲染阶段对齐像素；移动与物理状态仍保留必要精度。关闭 `imageSmoothingEnabled` 可避免放大图片被平滑，但不会自动把所有 Canvas 矢量绘制变成像素画。[MDN 图片缩放说明](https://developer.mozilla.org/en-US/docs/Web/API/CanvasRenderingContext2D/imageSmoothingEnabled)

对于 844×390 等非 16:9 横屏，优先保持纵向视野、扩展两侧世界范围，不拉伸人物。若设备不能整数倍铺满，允许统一最近邻缩放或小幅留边，以移动时不闪烁为验收标准；不要对每个素材各自选缩放倍数。

### 5.2 色板与材质

沿用项目已有的橄榄绿、泥褐基调，先冻结一个晴天母版，再制定其他天气。下表是建议色板，不是原作采样。

| 色组 | 色值建议 | 用途 |
|---|---|---|
| 林地暗面 | `#27352D`、`#3A442F` | 树后、灌丛内部、前景压边 |
| 草与苔 | `#50603E`、`#68764E`、`#879064` | 草地大面与少量受光草簇 |
| 土路 | `#6F5A43`、`#8D7657`、`#A38D68` | 路面、干土与踩踏边 |
| 木材 | `#4C3D2E`、`#6D5840`、`#927653` | 木柱、篱笆、器物；纹理顺材质走向 |
| 陶与土墙 | `#805E47`、`#A17C5A` | 陶器、墙面、窑体 |
| 麻布与浅衣 | `#B6B09A`、`#D1C9AC` | 角色识别与有限亮部 |
| 点缀 | `#B68138`、`#D4BF77`、`#405C55` | 秋叶、小花、冷色灌木 |

每种材质先用 3–5 个主色阶，少量共享过渡色。画面可以有更多颜色，不要求全屏只有五种颜色。暗部保留冷暖差，避免全屏黑色遮罩压暗。晴天窗户默认呈暗孔/反光；暖光只在确有火光或灯光时出现。

### 5.3 构图与层次

每个视口先安排一块主要可行走空地、一个焦点和两个方向线索。房屋不必居中，主路不必十字交叉，树木不沿边框排队。

推荐层次：地面大色块 → 路缘与地被 → 低矮物件 → 可按脚底排序的人物/树干/墙体 → 独立屋顶与树冠 → 克制的天气与粒子 → UI。

树冠、屋顶遮住玩家或选中目标时局部淡出；碰撞根据树干、墙体、围栏，不根据整块透明贴图的矩形。常规主路保持完整可辨认，密林探索区可用短时遮挡增加氛围。

### 5.4 动画

角色起步使用四方向；待机每方向 2 帧，行走每方向 6 帧，基础工作每方向 4 帧，共 48 帧/角色模板。第一阶段用一个完整模板验证脚步与锚点，再派生衣服与发型。不要未经预算就同时承诺八方向、所有工具和所有年龄段独立全套动画。

树叶主要做局部小幅变化，避免整张树像橡皮伸缩；火焰、烟、水波、落叶分别控制节奏。村口有人走动、窑边有人添柴，比增加几十个无意义漂浮光点更能传达生活。

## 6. 横屏少文字：具体交互方案

默认探索时，让地图占据绝大部分画面。常驻信息只保留地点短名、日期/季节、真实行动额度、紧急需求和少量入口。

布局：左上地点与简短时间，右上暂停/菜单；左下可选移动控制，右下交互按钮及行囊入口。熟人、人生、地图放进一层简短菜单，避免五六个大按钮长期覆盖景物。按钮触区按 48 CSS px 起步，图标可小于触区。

默认点击地面行走，点击人物/物件先选中；展示短动作条，再决定是否执行。可选虚拟摇杆，使用同一移动与碰撞接口。桌面保留 WASD/方向键、交互键和取消键。

| 场景 | 默认显示 | 展开后显示 |
|---|---|---|
| 普通探索 | 场景与少量 HUD | 地点介绍、世界背景 |
| 接近陌生人 | 外观描述或“陌生人”，2–3 个动作 | 交谈内容与已知信息 |
| 操作工具/资源 | 名称、动作、成本 | 材料、产出、归属与限制 |
| 不能行动 | 一条最直接原因，如“缺柴 2” | 所有条件与恢复途径 |
| 动作完成 | 图标＋“柴 −2，熟食 +1” | 完整过程和日志 |
| 请求/约定 | 一句请求＋可见期限 | 条件、承诺、已知后果 |
| 重大人生变化 | 明确的短卡片 | 细节、关系、历史记录 |

原来的“在场人物列表”和“所有出口列表”退出默认画面。名字只在选中、接近或人物需要注意时出现。未知身份仍按玩家认知显示，不能为方便地图标注泄露真名。

低文字不等于隐瞒代价。例：把“现在去窑场可能要耗费今天的一部分精力”改为“去窑场 · 行动 1”；该数值必须来自服务端。不能用纯图标让玩家猜自己是否会跨日、消耗物品或承担承诺。

远处目标：先展示走近预览，耗材/交易动作抵达后再确认；途中可取消。若成本、目标位置或权限变化，清楚更新条件，不能照旧扣款。多人或物件重叠时提供小列表选择。触屏草丛中小物件允许扩大命中范围，但不能抢走附近地面的移动点击。

对话时保留场景背景，底部最多两行当前话语、两三个短选项；完整往来进入日志。重要道德选择不为追求短句删掉必要信息。

## 7. 第一张地图与首轮可玩内容

首轮建议一张约 96×64 格的村落核心地图（16px 格对应 1536×1024 逻辑像素），再配一个小型室内与一段河岸/林径。地图尺寸是制作上限建议，先灰盒验证步行节奏，空洞则缩小。

村落关系示意，实际布局避免对称网格：

```text
             林缘 —— 采集支路
               |         |
    居所 —— 公用空地 —— 粟田
      |          |         |
    晾晒区 —— 窑场小路 —— 河岸/取水点
```

首轮五类锚点：家门（休息/储物）、公用空地（相遇/消息）、窑场（手艺/合作）、粟田（劳作/供给）、河岸（取水/探索）。这些是玩法空间职责，不要求立刻把所有现有 Place 合并成同一实体；地图区域需要映射回既有地点与权限。

每个区域都要有：入口、可走路径、主要工作点、等待站位、对象摆放点、退出路径。装饰节点和真实实体分开，不能把背景柴堆误画成可取用但无规则支持的资源。

熟悉后的主要相邻活动点，建议纯步行 5–12 秒；连续超过 20 秒没有观察、抉择或资源，就缩短路线或增加内容。此为节奏目标，不预先假设玩家觉得越大越好。

**首个 15–20 分钟切片：秋雨前的一捆柴。**

1. 玩家从家门出来，看见屋檐损坏和晾晒物；背景中有人取水、有人在工作。
2. 在主路遇到居民借柴，短句说明请求和期限。
3. 玩家可留柴修屋、交出部分柴、以其他物品协商，或暂缓决定；只开放当前规则支持的选择。
4. 去窑场做一次真实工作：原料减少、半成品或产出出现，动作与物品状态一致。
5. 推进到下一结算节点，观察屋顶、柴堆、晾晒或 NPC 行为的变化；再问一句简短对话了解已知后果。
6. 保存退出后恢复，世界状态、物品数量、位置与承诺一致。

复用 `FIRST_SEASON.md` 的修屋、借柴、烧窑冲突。每个事件新增字段至少包含：触发条件、对象 ID、玩家已知信息、选项成本、NPC 自行处理策略、结果状态、可见变化、延迟后果、失败恢复、冷却和去重键。视觉变化是正式世界结果的映射，不能按演出需要凭空消耗或生成物品。

## 8. NPC 自主生活与时间方案

当前项目已有自治能力，近期应补“玩家看得见的自主生活”。不把随机走路、头顶冒泡当成自主行为交付。

先给 6–8 名重点居民明确住处、工作点、公共停留点与日常动机。示例为策划角色职责，接入时映射现有居民 ID，不凭空新增一批同名人物。

| 动机 | 画面行为 | 必须对应的世界事实 |
|---|---|---|
| 缺少食物 | 去交换或求助，工作安排改变 | 真实库存、交易结果、需要变化 |
| 参与烧窑 | 前往窑场并在工位停留 | 已有工作状态及参与者 |
| 天气转坏 | 收拾晾晒、进入遮蔽处 | 规则支持的避雨/收取状态；未支持时只做外观演出 |
| 履行约定 | 在约定区域等候或准备材料 | 真实约定、有效期限及可中断条件 |
| 关系变化 | 交流对象或短句发生变化 | 玩家可知的关系经历，不显示全知好感数值 |

建议先采用**行动推动模拟、动画实时呈现**：走路与查看不直接让角色老一天；有成本的行为沿现有额度结算，跨日沿原有世界时钟。NPC 决策跟随权威模拟节点；行走动画展示已发生/已批准的目标变化。没有真实日内阶段之前，HUD 不显示伪造的 08:30。

下一阶段再讨论“晨、昼、暮、夜”等世界级阶段。阶段必须由同一权威时间系统导出，存档记录，避免第二套独立时钟。阶段推进需要明确影响饥饿、生产、承诺、新闻和远行，先做兼容设计再接入。

每名角色路线需处理目的地不可达、门被阻挡、玩家打断、目标失效和过期任务。NPC 离开视野可以抽象结算，回到视野时落在合法入口或既有位置；不能在玩家眼前每次刷新随机换位置。

## 9. 美术生产路线与素材清单

| 路线 | 好处 | 主要成本/风险 | 建议 |
|---|---|---|---|
| 全程序化绘制 | 复用当前代码快、参数易改 | 容易出现重复圆树、统一噪声、缺乏有意构图 | 保留作细节与变体工具 |
| 全手工逐场景绘制 | 构图和风格控制强 | 大量场景与状态重画，交互遮挡拆分成本高 | 用于风格母版与重点场景 |
| 手工骨架＋模块素材＋程序细节 | 风格与复用兼顾 | 需先统一资产规格和地图契约 | 推荐主路线 |

制作顺序：先灰盒构图 → 一名人物＋一棵树＋一栋房的比例板 → 640×360 母场景 → 拆素材 → 接入可行走场景 → 天气/季节变体。第一张母场景没有通过，不批量生成树和房屋。

| 素材包 | 首轮范围建议 | 必须包含的状态/元数据 |
|---|---|---|
| 地表 | 草、土、泥、水、耕地 5 类 | 边缘/角落、破口、少量变体；是否可走另存 |
| 乔木 | 3 类树形，各 3 变体 | 脚底、树干碰撞、树冠遮挡、阴影 |
| 灌木/地被 | 灌木 6、草簇 6、花簇 4、岩石 4 | 避免相同高亮重复；区分装饰与障碍 |
| 建筑 | 居所、作坊/窑场、储物棚 3 套 | 墙、屋顶、入口、工作/存放锚点 |
| 围栏/桥/路标 | 一套可拼接构件 | 转角、尽头、缺口、门与通行宽度 |
| 日用物 | 陶器、柴、粮袋、工具等 16–24 类 | 空/满、可拿/固定、损坏或制作中 |
| 人物 | 1 套完整基础动画，6–8 个识别外观 | 同脚底、朝向、持物点、帧时长 |
| 世界变化 | 湿土、收割地、修屋、晾坯/成品 | 由规则驱动，不与天气贴图混为一谈 |
| UI | 12–16 个常用图标 | 选中/禁用/按下，短标签与无障碍名称 |

上表是范围估算，自动拼接边缘和动画会放大实际帧数。试做一个素材包后再报价或估工期，不能把“24 类物件”理解成“24 张图就做完”。

Aseprite 可按图层和动画标签导出精灵表；适合把待机、行走、工作等序列统一交付。[Aseprite 精灵表文档](https://www.aseprite.org/docs/sprite-sheet/)

地图编辑可采用 Tiled：地面用 Tile Layer；交互点、碰撞、出生点与自定义属性用 Object Layer；前景组织为独立层。这样画面形状与通行规则不必强行共用一个矩形。[Tiled 图层文档](https://docs.mapeditor.org/en/stable/manual/layers/)

每个素材交付原始可编辑文件、透明 PNG/图集、元数据和来源记录。建议字段：assetId、version、nativeSize、pivot、collision、occluder、animations、paletteId、variants。素材包中明确“缺的是哪一帧”，避免渲染器静默用错误图片替代。

AI 适合帮助做构图候选、色板探索与素材草稿；正式素材仍需校正像素网格、视角、脚底、遮挡和帧间一致性。不要把一张漂亮 AI 场景图切碎后直接当作可靠地图，也不要仅做缩小再放大就认定是合格像素资产。用户参考图只作为视觉参照，交付资产单独记录来源与授权情况。

## 10. 技术接口建议：让另一位 AI 能独立接入

沿用已有 TypeScript 模拟与 Web 渲染，先不为画风重写引擎。画面品质首先取决于素材、构图和层次；更换渲染库不能自动修正人物排队或树形重复。

建议四层契约：

| 层 | 管什么 | 不能管什么 |
|---|---|---|
| 权威模拟 | 地点/位置、物品、权限、成本、时间、NPC 决策 | 不知道素材图集与屏幕坐标 |
| 玩家可见投影 | 当前可知的人、物、动作与可观察状态 | 不输出隐私真名、秘密或隐藏动机 |
| 地图内容 | 稳定对象 ID、通路、入口、碰撞、工作锚点、素材引用 | 不自行创造库存和关系 |
| 渲染与输入适配 | 显示、选中、路径预览、动画、提交意图 | 不直接改世界、不另算行动成本 |

输入输出建议而非现存接口声明：

- 地图：mapId、layoutVersion、worldBounds、layers、collision、portals、anchors。
- 动态对象：entityId、position、facing、visualState、knownLabel、availableActions、revision。
- 操作请求：actorId、targetId、actionId、expectedRevision；位置校验与成本由服务端完成。
- 结果：成功/拒绝码、已消耗资源、实际产出、受影响实体、最新投影；拒绝后前端撤销预测动画或重新同步。

关键边界：同一物件取走后，其余物件不能按数组顺序重新排队；位置绑定稳定 ID。布局升级按版本迁移，旧位置失效时迁到最近合法点并解释，不删旧存档。重复点击和网络重试不能重复扣料；同一客户端应串行提交会改变位置/世界的动作，服务端再用修订号或幂等机制兜底。

若使用逐步移动，渲染帧率与服务端动作频率必须分离；不要每一绘制帧发一次网络命令。每格还是每段路径提交由实现者基于现有接口决定，但都要支持取消、碰撞更新和存读档恢复。

## 11. 性能、显示与可读性预算

首轮目标：真实目标手机持续运行至少 10 分钟，30fps 为最低体验目标；桌面争取 60fps。记录中位数、P95 帧时间、明显长帧、资源峰值、设备/浏览器/分辨率与温升感受。这里没有任何已测通过的声明。

静态地形、重复树形和建筑预渲染/缓存；人物和天气单独更新。只绘制可见区域和必要外扩边界，页面隐藏时暂停绘制。MDN 官方优化建议涵盖重复图形预渲染、整数绘制坐标与分层 Canvas，可作为当前 Canvas 路线的优化依据。[MDN Canvas 优化](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)

降级顺序：粒子数量 → 大气叠层/动态阴影 → 背景装饰动画。保留人物、入口、交互反馈和文字清晰度。背景美术复杂不能成为玩家看不清按钮的理由。

建议覆盖横屏 740×360、844×390、932×430、1280×720 CSS 视口，并在至少一台目标手机验证；模拟器截图只写成模拟证据。检查安全区、浏览器地址栏伸缩、字体放大、切后台、旋转与误触。

## 12. 实施顺序、放行条件与工作边界

本方案不改变正在进行的开发任务。建议由现有负责人在一个交付节点后采纳以下顺序，不要求中途停工或整套推翻。

| 阶段 | 交付物 | 放行条件 |
|---|---|---|
| A 风格冻结 | 比例板、色板、一张晴天母场景、一张林缘场景 | 缩到手机实际尺寸仍辨认人物/道路/入口；树形与构图接近参考方向 |
| B 可复用美术 | 地表、人物、树、建筑、道具素材及元数据 | 素材统一像素尺度、脚底锚点和光向；地图拼接无明显破口 |
| C 横屏交互 | 正式入口、行走/选中/互动/返回、稳定位置 | 玩家完成取物或劳作；成本和结果真实；地图可恢复 |
| D 世界会生活 | 重点 NPC 可见日常、物品与工作状态变化 | NPC 自主结果与画面一致；玩家不介入仍有合理处理 |
| E 一段完整生活 | 秋雨前的一捆柴、至少两条合理路线 | 当下及延迟后果可观察，保存恢复不丢失，世界不因玩家缺席停摆 |
| F 扩季节与区域 | 雨/雾/雪、更多区域、日内阶段兼容方案 | 完成前面环节后再扩，不靠大量新场景掩盖交互缺口 |

先用实际完成 A 和一个素材包的时间校准产能，再排期。未知开发者投入、美术产能和现有任务完成度时，不承诺“几天整套完成”。

验收必须分开：静态风格相似、动态画面稳定、规则正确、手机实际可玩。代码测试成功只覆盖其中部分。

建议同参数对照留档：用户参考图、已有基线、改进图三栏；记录场景 ID、版本、天气、季节、镜头、动画时刻。比较时先看构图和角色比例，再看材质，最后看粒子。色板合规、文件可打开、截图漂亮都不能代替互动验收。

最低玩家路径清单：

- 进入游戏即看到横屏地图，能找到自己、道路、家门和主要操作。
- 从家门走到目标，选中并执行一次真实动作，看到成本与结果。
- 树冠遮挡下仍能定位角色；密集对象可以准确选中。
- NPC 从一个活动点转到另一个活动点，其目的与真实状态相符。
- 缺材料、路被挡、目标离开或状态过期时有简短而明确的恢复提示。
- 雨天、夜间外观（若已接真实时段）、雪景不掩盖重要交互信息。
- 保存、退出、继续后位置、物品、关系与承诺正确；旧档迁移有版本策略。
- 玩家不给全村指令，也能观察到别人对自身需要作出的行动。

## 13. 可直接转交的简短任务说明

> 在现有任务的下一交付节点采用本方案：目标为横屏、少文字、低饱和自然比例像素乡野，玩家单人行动、NPC 自主生活。先做一张可行走母场景，优先修正对称构图、圆球树、排队人物和遮挡；以统一逻辑像素和稳定脚底锚点交付素材。采用现有模拟与权限，所有物品、成本、时间和 NPC 结果来自真实世界。先完成家门→遇人→劳作→结果→保存恢复，再扩季节和区域。交付同参数对照图与实际操作证据，分别说明美术、规则和手机体验的完成程度。

这段说明仅供用户转交，本轮没有发送给任何其他 AI。
