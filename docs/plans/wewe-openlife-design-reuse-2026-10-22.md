# WEWE 旧作设计回收与 OpenLife 融合需求及执行计划

> **状态：提案 / 待审计，不代表开发任务已获批准或已实现**  
> 日期：2026-10-22 · 版本：v0.1  
> 来源：`Zhangwier/WEWE`（历史 Python 游戏原型）  
> 目标：`Zhangwier/OpenLife`（当前 TypeScript 人生模拟项目）  
> 主计划：[长期游戏设计与完善计划（2026-10-22）](long-term-game-design-2026-10-22.md)；本提案是补充，不覆盖其阶段和优先级。  
> **本次授权范围仅为撰写计划文档。** 后续接手者必须先做只读审计；不得把本文当作“立即实现全部功能”的指令。

## 1. 决策摘要

**建议回收的是设计问题与行为案例，不是直接移植 Python 代码。** WEWE 存在两条不同方向：

1. `module/Chat.py`：世界、建筑、智能个体、性格、记忆、请求池、意图池、情绪、物品与交易。多数复杂行为尚停留在接口、注释或 `pass`，属于**原型构想，不是经过验证的完整 AI 系统**。
2. `module/GameBuild.py`：基于 Pygame 的精灵帧动画、移动、碰撞和基础游戏循环；`rescouse/` 包含 2D 像素资源。它适合视觉技术参考，但不适合替换 OpenLife 的 Web 交互或模拟内核。

OpenLife 已有正式的事务、事件、确定性 RNG、世界实体关系与存档架构，NPC 部分也已经具有性格、需求/目标决策、个人见闻、信任和怨气。因此**不得重新造一个平行的 WEWE 人物引擎**。只有在现有能力验证出体验缺口时，才提出最小原生增量。

## 3. 产品目标与非目标

### 3.1 核心目标

让 6–8 位核心 NPC 不只是执行日常任务，还能**在自身知情范围内**因为共同经历、个人性格、需求与关系变化，作出可解释且互不相同的下一步决定；玩家能在数日、换季乃至下一代看到部分实际后果。

首要玩家价值：
- **有理由的选择**：NPC 会帮助、拒绝、协商、改变主意；不是固定好感度阈值或随机台词。
- **有来源的记忆**：亲历、转述、误传、重要约定区分来源；人物可能不知道，也可能记错或遗忘。
- **能延续的因果**：人物的当前行动、资源和约定与过去事实对应，玩家能追踪，不能靠预设文案假装世界发生了变化。

### 3.2 明确不做

- 不把 WEWE 的 `Chat.py`、`GameBuild.py`、`GetHumanData.py` 复制/转译到 OpenLife；不引入 Python/Pygame 运行依赖。
- 不重写 `packages/kernel/`、世界事务、事件、权限、时间、RNG、存档内核；不增加第二套事件真相或知识库。
- 不开发全员大模型实时对话、全图实时路径碰撞、复杂战斗或大规模 3D。
- 不默认扩展几十种性格参数，不先追求“数值越多越真实”。
- 不假设所有 WEWE 美术都是可再分发资源；没有来源/授权证明之前不得移入正式内容包。
- 不让 NPC 读取开发者全知世界快照来决定自己“知道”的事情。

## 4. 候选需求：仅在差异审计确认确有缺口后进入实现

### R-01：重要经历的跨时间记忆（优先验证，非预定重构）

同一 NPC 能区分临时消息、长久关系及少数重大经历（如救助、失约、严重冲突、共同完成的作品）。对每段“可行动记忆”应能解释主体、事件引用、知情来源、发生/获知时间、保留/失效条件；具体 schema 必须复用现有事件、`social.ts` 与 `epistemic-state`，**先查已有结构，不新增影子账本**。

验收示例：某 NPC 过季后仍能在合乎其知情权限时体现“之前被爽约”；一般村务小道消息仍可过期。遗忘不等于删除世界历史；历史日志/记录是否保留由内核规则决定。

### R-02：请求—目标—决策闭环（优先审计行为而非接口）

在现有 NPC 大脑中验证 `接收处境/请求 → 判断需要、关系与可行方案 → 提出合法 Command → 获得执行结果 → 调整目标` 是否闭环。重点是**拒绝、改约、帮忙未果、第三方介入**；已覆盖的行为不重复开发。

验收示例：借柴请求被拒后，NPC 可以根据资源、熟人和时间改变计划；失败不会凭空获得物资，也不会在每个 tick 无限重复同一请求。

### R-03：人物差异必须可被玩家感知

至少挑选 2 位拥有不同性格/关系/实际需求的现有居民，在同样的可见困境下测试可能的不同决定；呈现选择原因（如“不信任你”“家里也缺柴”），但不泄露其秘密或真实未知事件。

验收不以“两个 NPC 必须选不同结果”为唯一标准；必须解释为什么同或不同，且结果来自实际规则与状态。

### R-04：记忆容量、遗忘与可重放

验证旧档、长时模拟和多代压力下的空间成本、回放一致性和来源隔离。若引入新的记忆摘要，摘要只用于个人决策与界面，不能改变原始历史、悄悄改写事实或绕开 Command/Rule/Effect 事务。

验收以固定种子对照、时间推进与存读档测试为准；不要仅靠“游戏看起来正常”。

### R-05：2D 视觉资源（暂缓、独立决定）

将 WEWE 的像素风格作为可选视觉参考清单；先查美术授权、分辨率、角色帧规格和 OpenLife 现有交互规范。**当前阶段不实施资产迁移或渲染重写。**

## 5. 代表性纵向测试场景

**场景：秋雨时的借柴与失约。** 与现行长期计划“第一个季节”兼容，使用当前仓库已有的真实居民、关系和物品 ID，不创造无效 ID。

- 初始：玩家与一名熟人有约；另一位村民需要柴火；村民之间存在各自的资源及已有关系，至少一人不能/不愿无条件帮忙。
- 路线 A：玩家守约，但拒绝借柴；对方自主改计划或求助其他人，后续互动应能解释分歧。
- 路线 B：玩家先借柴，及时解释或改约；资源从真实物品账转移，另一人物对承诺的理解依规则变动。
- 路线 C：玩家失约且不解释；相关 NPC 的短期回应与换季后的关系/记忆区别于 A、B。
- 消息：仅听说事件者不能凭空知道隐藏动机；本人亲历、转述和世界事实分开。
- 不介入：NPC 仍有可行动的自行处理路径，事件不应无期限等玩家。

上述是**设计上的测试条件**，不是声称现有代码已具备全部分支；首轮审计须标清“现成可测、部分可测、需新规则”。

## 6. 与现行 GD 计划的衔接

本工作不得抢占 [长期计划](long-term-game-design-2026-10-22.md) P0 的稳定性、三条生计验证与真实试玩。建议作为：
- **GD-06 的输入**：6–8 位人物卡与首批有理由的拒绝、协商、补救。
- **GD-11 的输入**：记忆容量/整理、日常与重要关系区分、历史隔离。
- **GD-05 的验证场景**：秋雨困境的数日/换季后果。

只有在 GD-01 的基线与 CI 收口可核实，并且已有行为缺口明确时，才将 R-01～R-04 中最小的一项拆为实际开发任务。不要让“回收旧作”成为新的独立大系统项目。

## 8. 技术与验证红线

所有后续变更遵守 OpenLife `README.md` 的 INV-001～INV-008：
- 世界状态仅由 `Command → Validation → Rule → Effects → Transaction → Events` 改动；AI/NPC 只提出合法命令。
- 同一状态、命令、种子、规则和模块版本必须确定性重放；不能使用 `Math.random()`、系统时间或外部模型输出来改写真实世界状态。
- `Fact ≠ Observation ≠ Knowledge ≠ Memory ≠ Belief`；人物私有记忆与公知、历史事件保持来源边界。
- 现有 `social.ts` 关系、`epistemic-state`、事件、存档为复用入口；不得平行保存不可核对的事实。
- 保存与读档、跨日/跨季、80 人压力、事件去重、物品守恒、知识隔离，以及固定种子重放在改动涉及范围内必须有回归证据。
- 正式修改前运行现有测试并留存基线；文档中历史的测试通过率不等于当天实际通过率。
- 同一工作区可能存在未提交变更：先列出，禁止清理、覆盖、重置或误提交别人的工作。

## 9. 交付格式与验收清单（面向 WebCodex/Codex）

**首次接手的明确任务：只做 A0 差异审计，不实现 R-01～R-05。**

1. 读取 `AGENTS.md`、`docs/AI_COLLABORATION.md`、`docs/plans/long-term-game-design-2026-10-22.md` 与本文。
2. 读取 WEWE 的 `module/Chat.py`、`module/GetHumanData.py`、`module/GameBuild.py`，有必要再看 `rescouse/` 和 `module/osmTOjson.py`。若无法访问私人 WEWE 仓库，明确列出权限阻塞，不能猜代码。
3. 核对 OpenLife 的 `autonomy/brain.ts`、`autonomy/mind.ts`、`social.ts`、`epistemic-state`、事件/存档/相关测试；必要时查 `village-wants`、`village-stories`、`story-director`，以真实代码为准。
4. 用表格记录每项：WEWE 原始设想／OpenLife 已有证据（文件+函数/测试）／确切缺口／用户体验收益／最小改动建议／冲突和风险／优先级／是否建议不做。至少对 R-01～R-05 分别表态，不得仅复述本文。
5. 列出 A1 最小纵向场景的真实世界对象、可复用命令与可能需要的新规则；不假定 NPC 全知，不绕过旧规则。
6. 把**已核实的事实、推测、未检查项**分开写；汇报仓库分支/提交、测试实际运行情况与因权限不可读取的项。
7. 将 A0 报告交给用户审阅；除审计文档外不修改生产代码，不提前实施、搬运素材或批量创建任务。

**A0 验收：** 能明确回答三个问题：(a) WEWE 有哪些独有、且真正值得带进 OpenLife 的设计？(b) OpenLife 已经实现了多少，剩下的最小缺口是什么？(c) 如果只做一个改进，应该是什么、怎样测得它真实改善了玩家体验？
