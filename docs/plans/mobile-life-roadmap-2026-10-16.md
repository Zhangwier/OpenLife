# OpenLife 手机优先开发规划 · 2026-10-16

状态：基于 GitHub `main@035ff3b` 与本次分支整合的实施建议。这里的排期、数量、性能指标是待验证目标，不是已达成结果。Core 约束仍以根目录 `需求书.txt` 为准；本文件更新近期优先级，不撤销既有需求。

## 1. 产品决策

**先做一款能在手机上反复玩下去的“小聚落人生模拟”，把一个人的生活、村民关系和家庭延续连接起来。**

当前最大的价值是世界会记得行为，村民拥有自己的物品、需要与选择；当前最大的风险是功能数不断增长，但玩家仍不能自然理解“今天想干什么、为什么失败、明天为什么回来”。下一轮以完整体验验收，不以新增按钮、包数量或测试数量验收。

- 首个稳定版本：单人、一个河岸聚落，默认竖屏文字与轻场景；每天可玩 5–15 分钟，也可连续体验 30–60 分钟。
- 核心循环：发现生活需要 → 在几种办法间取舍 → 行动消耗时间/物资 → 人物与环境回应 → 留下记忆/作品/承诺 → 产生下一个自主目标。
- 三条同等有效路线：务农与饮食、纤维与修补、制陶与交换。允许跨路线，不把制陶当唯一主线。
- 中期目标：一个季节里形成自己的分工与两三段关系；远期目标：接班者继承一个已经被改变的世界。
- 暂缓：多时代全量内容、大规模无缝地图、实时联机、全员大模型对话、付费商业化、重型 3D 重写。保留扩展边界，不提前建设空壳系统。

## 2. 当前工程事实与缺口

核对范围包括源码、工作区清单、现有需求、单元/HTTP 测试和当前浏览器入口。未以真人长时试玩代替检视，不能据此声称趣味性已达标。

| 领域 | 当前证据 | 下一步真正缺口 |
| --- | --- | --- |
| 引擎 | 11 个 packages，36 个模块包；事务、确定性、历史、存档、自治运行时已存在 | 核心应保持稳定；补性能与迁移证据，避免为新玩法改 Core |
| 聚落 | `settlement-locations` 含地点、实物、食物、工地、配方、天气、婚恋、家庭、出身、愿望等 | 单个 `module.ts` 拆交易后仍约 5,200 行，规则注册、视图和内容耦合 |
| NPC | `autonomy/brain.ts`、性格、社交见闻、求助/交换、村民消息已有实现 | 需要解释与体验节奏；不能再把“NPC 自主行为”整体列为未实现 |
| 记忆 | `social.ts` 区分看见/听闻，新闻限制条数与有效期 | `seen/bonds/asked` 尚无统一字节预算、压缩版本和完整来源上限；不等于 MEM-001–006 完成 |
| 时间 | `world-clock` 与既有时间 RFC，行动额度和跨日流程已有实现 | 玩家可见耗时、过季中断、婚育/生产跨边界要统一验收，不能重定义 tick |
| 前端 | 原生 ES modules；默认 text，picture 仍是后续入口；theme/stage CSS | 手机信息层级、触控、无障碍、前后台恢复；图片模式缺资产，不能作为已完成卖点 |
| Web | Node HTTP 服务 + 一个进程内共享 Simulation | 适合本地/受控试玩，尚非多用户个人存档服务；服务器落盘不等于手机离线 |
| 内容 | `river-terrace.json`、`river-terrace.people.json` 和加载校验 | 内容覆盖矩阵、条件组合检查、重复事件控制、可维护的编辑约定 |
| 验收 | 大量规则/HTTP 测试；旧浏览器脚本绑定已删除 SVG | 更新当前文字版验收；引入真实 Android/iOS 和不指导试玩记录 |
| 文档 | 旧需求仍把若干已实现功能列作 M2–M5 待开发 | 保留历史记录，在新状态矩阵标记：有代码/自动验收/真人验收/未做 |

## 3. 同类游戏：借鉴什么，如何落在本项目

调研时间 2026-10-16，依据官方功能介绍。下表“落地”是设计推论，不是对其他游戏内部源码的断言；不复制其美术、剧情或界面。

| 参考 | 官方可确认的特点 | OpenLife 落地 |
| --- | --- | --- |
| [Stardew Valley](https://www.stardewvalley.net/about/) | 农事、技能、日程各异的居民、关系与季节活动 | 用季节与熟人变化组织长期目标；每天只推荐少量可做的事；承诺/约定可追踪，不把所有人做成交易菜单 |
| [Roots of Pacha](https://rootsofpacha.com/) | 石器时代聚落、发现工具与想法、食物加工、陶艺、共同体关系 | 最贴近本项目题材。把生活难题、实践发现、技艺传播和公共改善连起来，避免只用经验条解锁配方；历史适用性另作内容审查 |
| [RimWorld](https://rimworldgame.com/) | 需要、性格、关系与事件讲述者共同构成故事 | 从世界已有压力中挑选少量可解释事件；事件不凭空改库存/关系，仍通过 Command 校验；提供舒缓与困难节奏 |
| [Wildermyth](https://wildermyth.com/) | 人物成长、老去、关系和有后果的选择；角色可成为传奇 | 生成人物自己的生涯摘要与传家物来源；接班后旧人旧事继续影响世界。OpenLife 采用连续世界，不照搬其跨冒险角色复用 |

具体建议：学习 Stardew 的“每日可理解”、Pacha 的“共同生活与发现”、RimWorld 的“因果故事”、Wildermyth 的“人物留下痕迹”。第一阶段只完成一个小聚落的密度，不同时追求四款游戏的内容规模。

## 4. 手机信息架构与交互

### 4.1 主要页面

保留当前四个主入口并简化文案为“此刻、行囊、熟人、人生”；地图、制作、存档、家谱放在相关上下文，避免增加一排一级导航。

1. **此刻**：顶部日期/地点/天气和最重要的一项需要；中间当前人、物与最近发生的事；底部移动、做事、休息。默认只显示 2–3 个上下文建议，可忽略，不做强制任务。
2. **行囊**：按用途分组，显示数量、负重、归属/借用；选择物品后再出现使用、放下、赠送或交换。归属未知应显示未知。
3. **熟人**：先列真正认识且有当前联系的人；详情显示玩家已知信息、最近共同经历、未履行承诺；不暴露 NPC 全部内心账本。
4. **人生**：自己的需要、技能和阶段目标；作品、家庭、家谱、生活日志从这里展开。开发诊断信息留给调试工具。

### 4.2 操作规则

- 手机点击对象后开一层详情页/底部面板；系统返回先关面板再返回上页；保留列表滚动位置，不堆叠多个弹窗。
- 提交前显示材料、耗时、必要条件与可观察风险；禁用按钮必须有原因和可行下一步。危险/不可逆操作才二次确认。
- 一次点击只提交一个操作；重复点击不会重复扣料。成功反馈说明实际变化；失败不使用“未知错误”覆盖规则拒绝理由。
- 关键触控区至少 48 CSS px（原生壳按平台逻辑尺寸复核）；正文建议 16–18px；支持系统字体放大、安全区、横竖屏转换、减少动画。
- 360/390/430px 测布局，实际 Android 与 iOS 测触控和输入法；200% 文字缩放不遮住确认/返回；读屏可读人物、物品与操作结果。
- 文字版先稳定。场景图是同一份投影的另一种展示，不得独立决定可交互对象、距离或交易资格。

### 4.3 第一小时的体验脚本（非强制任务线）

| 时间 | 希望发生 | 可观察验收 |
| --- | --- | --- |
| 0–2 分钟 | 选名字/出身后马上见到自己的处境；可跳过说明 | 无提示完成一次有效行动，知道时间或物资发生了什么变化 |
| 2–10 分钟 | 食物/容器/修补之一形成小目标，可自做、借、换或求助 | 至少两条合法解决路径，失败有恢复办法 |
| 10–30 分钟 | 认识 2 人并看到其需要，自己的帮助或拒绝被记住 | 下一次见面出现可追溯的不同回应，物品账仍正确 |
| 30–60 分钟 | 完成一件作品/承诺，看见天气或季节带来的变化 | 玩家能主动说出下次想做什么；存退再进保留世界 |

## 5. 架构调整顺序

遵循 `packages → modules → apps` 的依赖边界，先在现有包内部形成职责清楚的文件，不为每个动词创建 workspace。

| 边界 | 建议职责与最小接口 | 禁止混入 |
| --- | --- | --- |
| `settlement-locations` 注册入口 | 汇总注册规则/反应/投影，保持现有 public exports | 大段配方、对话模板、浏览器格式化 |
| 交易规则 | `barter.ts` 保留已有交易；后续归并一般交换时沿真实命令语义设计 | 第二套库存、绕过对方同意的转移 |
| 家庭/关系规则 | 婚恋、照料、承诺、继承按现有 ownership 声明产出 Effects | UI 直接改组件、临时复制人物资料 |
| 生活生产规则 | 食物、劳作、配方、空间可达性；读权威物品关系 | 平行“库存数字”与真实物品不一致 |
| 个人认知 | 有界记忆读写、可访问来源、确定性压缩 | 从全局历史自动补全角色未曾得知的事实 |
| 玩家投影 | 输入 WorldView + actorId，输出可见场景/可用操作/原因 | 全知账本、客户端重新计算规则 |
| 应用运行时 | 建局、dispatch、推进、保存、加载的一组稳定方法 | HTTP 路由与页面 DOM |
| 持久化适配 | 读取/写入已版本化 SavePackage，串行写、失败可恢复 | 拥有第二份世界状态 |
| 内容包 | 居民、地点、配方、事件条件及本地化文本 | 文件中执行任意脚本 |

第一刀建议把 command/component ID 与纯类型移到 `schema.ts`，消除 `module.ts ↔ barter.ts` 等文件级回环；工作区无环测试目前只检查包级，不能证明文件级无环。随后按“交易 → 生产 → 关系/家庭 → 投影”小步抽取，每次用原有公开行为测试保证等价；行数下降是结果，不是唯一验收。

对移动离线先做技术验证：当前 `content.ts` 使用 Node `fs` 加载 JSON，`server.ts` 组合 HTTP 与 Simulation，不能直接打包进浏览器。先区分“内容数据注入”和“平台文件读取”，再验证 Worker 中模拟与 IndexedDB 存档。确认第二种实际运行环境后才引入共用适配接口；不用空泛的多平台框架替代这项验证。

## 6. 分阶段执行与验收

以下按 1 名主要开发者、已有内容基础估算，为工作日范围；美术、设备覆盖和真人反馈另计。每一阶段达标才进入下一阶段，大模型辅助不等于固定产能。

| 阶段 | 时间参考 | 交付 | 放行条件 |
| --- | --- | --- | --- |
| S0 当前基线收口 | 2–4 天 | 分支整合、启动/存档修复、功能矩阵、当前模式浏览器验收 | 全套测试、两个 CLI 演示通过；新局/行动/存退恢复可用；不存在启动阻断 |
| S1 手机可理解的生活 | 5–8 天 | 四页信息层级、统一行动面板、失败恢复、三条生活路线梳理 | 三名首次玩家各完成 20–30 分钟不指导试玩；至少 2/3 在两分钟内有效行动，并说出一个继续目标 |
| S2 人与因果连续性 | 7–10 天 | 人物需要/承诺投影、有界记忆、来源与遗忘、确定性事件节奏 | SCENE-A/B/C 跑通；相同轨迹重放一致；拒绝/失约/求助产生可解释后果，且无凭空物品 |
| S3 一个季节与社区 | 7–12 天 | 三条路线各有完整生产链、少量社区目标、季节影响、内容校验 | 各路线可独立生存并与他人交换；多种种子跨季运行无死局/无限套利；真人愿意续玩 |
| S4 家庭与传承 | 7–12 天 | 照料、分工、老去、交棒、传家物和因果生涯摘要 | 交棒前后财富/归属/关系/知识来源正确；旧人退出后历史可查；长时间推进可中断 |
| S5 手机运行与发布准备 | 7–15 天 | 离线方案落地或明确联网方案、版本迁移、真机性能、发布构建 | Android/iOS 设备矩阵通过；断网/前后台/进程终止与升级恢复有证据，存档导出可用 |

S1 与 S2 中只做支撑当前任务的模块抽取；不暂停玩法数周做一次“大重构”。S5 的离线可行性实验在 S1 就开始，正式打包放在玩法稳定后。完整路线约 7–12 个开发周，受反馈与离线实验显著影响，不能作为发布日期承诺。

## 7. 机制验收重点

- **交易/归属**：双方当面且同意；接受时重新检查物品、负重、借用状态；重复提交不重复结算；价格不是独立货币系统。
- **生活**：饥饿/疲劳提供取舍，不逼每分钟打卡；默认失败可恢复；连续生活遇到死亡风险、重大承诺、婚育或资源耗尽时停下来。
- **记忆**：事实发生时间与获知时间分开；传闻保留来源与置信度；压缩不得无限累积引用，遗忘后不能借全局日志恢复全知。
- **事件**：预条件、角色资格、冷却、效果和可观察结果均有测试；“讲故事”不豁免事务、库存、认知边界。
- **传承**：物品归属、债务/承诺、技艺学习、家庭历史分别定义可继承规则；子代不是父代数值复制。
- **内容规模**：先跑好现有一个聚落，新增地点必须增加一种交往/生产/迁移选择，而不是同一菜单换背景。

## 8. 手机技术路线与存档边界

近期继续 Web 文字版用于快速试玩。产品方向建议单人离线优先，但必须经过 MOBILE-01 验证；如果实现成本过高，可先交付明确联网的受控试玩版，不把 PWA 安装入口等同离线游戏。

候选顺序：浏览器 UI + Worker 模拟 + IndexedDB 存档验证 → 实机浏览器/PWA → 有平台能力需求再评估 Android/iOS 容器。微信小游戏若成为明确发行目标，再单独验证其运行时、包体、存储和审核要求；本规划不预设已兼容。

服务器当前是一份共享世界：同一实例不同浏览器会操作同一个 Simulation。正式公开试玩前，要选择“每人独立 worldId/存档与权限”或“明确共享世界规则”，并补访问控制、并发与滥用限制。仅设置 HOST 或自动保存不能解决这些问题。

存档至少区分 schemaVersion、模块版本、内容包版本和迁移记录。手动槽与自动槽分开；升级前保留可导出备份；磁盘定时保存只保证最近成功快照，断电/强杀不保证收到关闭信号。移动端采用动作后节流保存与后台切换保存，具体频率用实机测量确定。

## 9. 验证、性能和观测

| 层级 | 测什么 | 证据 |
| --- | --- | --- |
| 规则 | 权限、物品守恒、时间边界、同意、重复命令 | 定向 unit tests + 可复现 seed/命令 |
| 集成 | 新局→生产→交往→存档→重启；迁移/损坏/失败 | HTTP 测试、旧档 fixture、状态差异 |
| 浏览器 | 真触控、反馈、返回、存退再进、文本放大 | 独立端口/浏览器上下文，机器可读报告与截图 |
| 长跑 | 多种子跨季/跨代、记忆预算、快进中断 | 实体/物品/历史数量、存档体积、命令 p50/p95 |
| 真机 | Android/iOS、慢设备、断网、锁屏、进程退出 | 设备/系统/浏览器版本、重现步骤、录屏或日志 |
| 真人 | 无提示是否找到目标、是否愿意继续、是否理解因果 | 三条路线各一份试玩记录与修改决定 |

性能首轮延续原需求：100 个活跃 NPC、1,000 个物品、满预算记忆；远场另测 5,000 人。普通操作模拟 p95 <100ms、主线程不出现 >200ms 长任务作为目标，UI 先给及时反馈；先记录设备与基线再承诺指标。快进分批可取消，暂停与恢复不重复结算。观察 CPU、峰值内存、JSON 体积、载入耗时与电量趋势，不能只测桌面 Node。

本地调试观测优先：命令耗时、拒绝码、NPC 选择理由、记忆压缩前后大小、存档写入结果。公开遥测另做知情选择，不上传完整存档或角色自由文本。

## 10. 版本与协作约定

- main 保持可启动；短分支围绕一项可验收改变，合入时 squash；旧基线的补丁先与最新 main 对照，不整文件覆盖。
- 原始分支尖端使用 archive tag 保存；被新版完整替代的 PR 关闭并注明落点，不为了显示“已合并”重复回放旧代码。
- 一份 PR 同时给出问题、行为变化、存档影响与验证。新增内容先过引用/配方/条件校验。
- CI 跑全套测试、目录新鲜度和两种世界演示；浏览器测试按当前产品模式检查，不依赖已删除的素材。
- 每个里程碑更新此计划的状态表与验收报告；保留旧日期文档作为历史，不继续维护相互矛盾的多份“最新计划”。

## 11. 尚未决定的产品问题

这些不阻塞 S0/S1，可在首次手机试玩后决定：首发渠道（手机浏览器/Android/iOS/微信）、画面与纯文字的比例、目标年龄与难度、是否允许后台离线推进、是否需要共享世界。默认本路线为单人、操作驱动推进、舒缓难度、文字优先。任何改变都应评估对时间、存档与权限边界的影响。
