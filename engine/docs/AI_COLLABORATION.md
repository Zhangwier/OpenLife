# OpenLife AI 分工与协作指南

更新：2026-10-16。供拉取仓库后的开发、审查与内容协作使用。

这是项目的默认工作分配，不是模型能力排行榜，也不要求同时启动五个 AI。用户明确指派优先；同一模型可以在不同任务中承担不同角色。模型名称以用户实际使用的产品为准，平台别名或版本变化不影响角色定义。

## 1. 默认分工

| 模型 | 默认角色 | 本项目主要职责 | 交付标准 |
| --- | --- | --- | --- |
| Opus 5.5 | 技术负责人、复杂问题审查 | 模块边界、接口约定；事务、时间、存档、继承等跨模块问题；关键变更审查 | 简短设计决定、影响范围、接口约定、可检查的验收条件 |
| DeepSeek V4.1 | 模拟规则与后端开发 | 食物、生产、交换闭环；NPC 需要与记忆；服务端存档可靠性 | 可运行代码、适用的边界测试、固定种子与重现步骤 |
| Kimi K3 | 手机前端与交互开发 | 四主页面、行动面板、返回逻辑、触控、字体与安全区；消费服务端投影 | 浏览器实际流程、手机尺寸截图、清晰的成本/拒绝理由/结果反馈 |
| GLM 5.3 | 独立测试与工程检查 | 回归、异常输入、存档兼容、物品守恒、时间重复推进、依赖边界 | 可复现问题、失败用例、影响说明和修复后的验证；区分规则测试与体验验收 |
| Muse Spark 1.3 | 玩法策划、内容与体验评审 | 三条生活路线、人物愿望、条件事件、对话、失败恢复路径 | 结构化内容表、触发条件、分支后果、试玩问题清单 |

Opus 聚焦需要技术判断的关口，不必逐条审批文案与样式。GLM 的独立验收不能只复述作者的测试结论。Muse 可以检查界面和规则中的体验问题；接到实现任务时同样需要代码与验证证据。

仅有三个并行工作位时，常驻 DeepSeek、Kimi、GLM；Opus 在接口设计与关键合并前介入，Muse 在内容设计和试玩复盘时介入。实际工具权限不足时，交付范围限于可读取、可运行或可验证的部分，并明确限制。

## 2. 拉取后的开工顺序

1. 检查当前分支、工作区改动和远端状态。保留已有改动，记录本次基线 commit。
2. 阅读 [当前路线与任务表](plans/mobile-life-roadmap-2026-10-16.md)，找到任务 ID、依赖和验收条件；涉及 Core 时阅读根目录 `需求书.txt` 的相关约束。按需查 [模块目录](MODULES.md)。
3. 在任务说明/PR 中记录：角色、目标、基线、允许修改的文件、依赖接口、验收方法、集成负责人。没有明确任务时，先交付职责范围内的现状检查与建议，不自动执行整张路线图。
4. 并行修改前确认文件负责人；各自使用独立 worktree 和短分支，默认分支前缀 `codex/`。每个测试服务器使用独立端口；服务端持久化关闭或使用独立存档路径。
5. 在范围内实现、验证，再交付给指定审查者与集成负责人。单个任务不自动授权另外启动多个代理、对外发消息或发布产品。

## 3. 修改边界与接口协作

| 范围 | 默认负责方 | 协作约定 |
| --- | --- | --- |
| `apps/web/public/` 页面、样式、交互 | Kimi | 从服务端投影读取可见对象和合法动作；前端不重新定义交易资格、库存或时间规则 |
| `modules/` 玩法规则、`apps/web/src/` 投影、`apps/web/server.ts` | DeepSeek | 世界变更经 Command/事务；修改投影前与前端约定字段、拒绝码及兼容方式 |
| `packages/` 核心契约与运行时 | 本轮指定实现者，Opus 审查关键变化 | 先说明为何现有模块边界无法解决、兼容影响和验证方法；避免为局部玩法扩张 Core |
| `tests/` 与工程检查脚本 | GLM 主导独立验收 | 开发者仍补自己变更所需测试；双方约定具体测试文件，避免互相覆盖 |
| 聚落内容 JSON、剧情与配方设计 | Muse 起草，指定开发者接入 | 先核对已有 schema 和资源 ID；由一个负责人写入同一份 JSON，内容作者可先交付独立提案 |
| 跨模块设计与里程碑判断 | Opus | 给明确决定和理由；默认不与实现者同时修改同一文件 |

高冲突文件包括 `modules/settlement-locations/src/module.ts`、`apps/web/server.ts`、`apps/web/public/settlement.js` 和聚落内容 JSON。文件归属以本轮任务说明为准，不把表格理解为永久独占。

需要跨边界时，先写清接口输入、输出、错误与兼容行为，再由各自负责人实现。如果多人需要修改同一文件，将任务顺序执行或先形成可独立修改的职责边界；不能仅靠“各改不同段落”假定没有冲突。

## 4. 首轮任务建议

以下对应手机生活循环阶段，执行前确认是否已完成或已有负责人。

### Opus：行动接口与规则边界

阅读当前规划与真实代码，明确手机行动面板需要的数据接口：成本、条件、不可用原因、结果反馈。审查是否泄露角色未知信息，是否重复实现权威规则。本轮以设计与审查为主。

完成条件：接口覆盖三条生活路线中的代表动作；明确前后端修改范围和验证方法；不能仅给通用架构图。

### DeepSeek：三条生活路线闭环

逐步跑通务农饮食、纤维修补、制陶交换。检查缺料、缺粮、借物和交易失败后的恢复办法。依据实际缺陷做小范围修复，并提供回归测试。

完成条件：每条路线交付 seed、操作步骤、预期结果与实际结果；失败路径不重复扣料、不凭空产生物品；新增规则保持确定性。

### Kimi：手机行动面板

沿用现有前端，呈现成本、不可用原因和实际结果；完善返回、字体放大与安全区。先使用约定投影，接口未就绪时明确临时数据与真实联调的区别。

完成条件：360/390/430px 下操作可触达、无横向溢出；实际浏览器完成选择对象→执行→查看结果→返回；提供截图与步骤。桌面模拟不写成真机验收。

### GLM：独立回归与边界检查

独立检查三条路线和存退恢复，优先找重复扣料、物品凭空生成、时间重复推进、旧档恢复失败。发现缺陷时先提供最小复现或失败测试，修复归属按任务约定。

完成条件：每项问题包含基线 commit、重现步骤、期望/实际结果、相关代码位置；修复后重新验证受影响路径。没有发现问题时也说明覆盖范围与未覆盖边界。

### Muse：六个生活事件

基于已有居民、地点与物品提出六个事件，每个至少两种解决办法。写清前提、参与者、材料、可观察后果、失败恢复与冷却。先核实已有内容，避免重复扩建大型系统。

完成条件：使用可查的内容 ID；区分已有能力与需要新开发的规则；不把纯文案描述算作已实现玩法。内容提案存放于 `docs/design/`，代码接入另外安排负责人。

## 5. 审查、合并与交接

作者完成适用的验证后，由另一角色独立检查。前后端联调由 Kimi 与 DeepSeek 对齐；GLM检查回归；Opus审查跨模块及存档/时间等关键变化；Muse关注玩家能否理解与形成下一步目标。小改动只安排必要审查，不要求五方会签。

每轮指定一个集成负责人；这个角色与模型名称分开，可以由用户指定的任何执行代理承担。其他参与者交付分支或 PR，集成负责人核对最新 main、解决冲突、运行必要检查、按授权 squash 合入并推送。保留原历史的归档处理应在分支清理前完成。用户已明确授权的范围内继续执行，避免重复索要确认。

交接使用以下格式：

```text
任务 ID / 角色：
基线 commit / 分支 / 当前 commit：
完成了什么：
修改文件与接口变化：
存档、时间、权限或内容兼容影响：
验证命令与实际结果：
重现 seed / 操作步骤 / 截图或报告路径：
未完成事项与已知限制：
下一位负责人需要做什么：
```

验证依据改动范围选择：规则和持久化改动执行相应测试，前端执行当前浏览器流程；最终整合执行项目要求的检查。历史测试数量不能充当本轮测试证据，未执行的检查明确标为未执行。

## 6. 一轮后调整分工

比较验收通过率、返工次数、实际耗时、额度消耗及工具可用性。把稳定交付的工作交给相应模型；需要帮助时交换角色或缩小任务。用户保留最终玩法与优先级判断，模型推荐不会自动成为项目决策。
